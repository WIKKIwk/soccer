# ARC-003 — UUID strategy

**Status:** Accepted  
**Decision date:** 2026-08-08  
**Depends on:** [ARC-001 modular-monolith boundary](ARC-001-modular-monolith-boundary.md)

## Decision

The platform uses UUID version 7 (UUIDv7) for newly generated canonical identifiers. UUIDv7 provides a Unix-millisecond time-ordered field while retaining random bits for uniqueness. This gives better database index locality than an unsorted random identifier without making the identifier a business timestamp.

UUIDv7 is specified by [RFC 9562, section 5.7](https://www.rfc-editor.org/rfc/rfc9562#section-5.7). The RFC describes the most-significant 48 bits as the Unix timestamp in milliseconds and the remaining value as random or implementation-defined monotonicity bits.

## Identifier coverage

UUIDv7 is used for all platform-generated IDs, including:

- administrators, roles, sessions, and actors;
- competitions, seasons, stages, groups, rounds, and ties;
- clubs, teams, persons, players, venues, fixtures, and matches;
- commands, command attempts, canonical events, audit entries, and outbox messages;
- imports, evidence references, quality records, and projection records;
- request and correlation IDs generated by first-party adapters.

Each domain identifier is a typed newtype around the UUID value, for example `TeamId`, `FixtureId`, `MatchId`, `CommandId`, and `EventId`. Raw UUID values do not cross domain boundaries where a typed ID can express ownership.

## Generation and storage

- IDs are generated at the application/infrastructure boundary through an injected ID-generation port.
- The domain accepts generated IDs through ports and does not call an operating-system UUID API directly.
- PostgreSQL stores IDs in the native `uuid` type with primary-key, foreign-key, and unique constraints.
- First-party `client_command_id` values are UUIDv7 and are wrapped as a typed command identity before admission.
- Public serialization uses the canonical lowercase hyphenated UUID representation.
- Database rows must not use a second, incompatible ID-generation strategy as a hidden default.

## Ordering and timestamps

UUIDv7 ordering is an index/locality aid only. It is not a business ordering guarantee. Match event order is defined by `(match_id, aggregate_version)` and command-local `event_index`; timestamps are explicit UTC fields governed by ARC-004.

Clock skew, multiple IDs created in one millisecond, and implementation-level monotonic counters must not change domain behavior. The generator may provide additional monotonicity, but consumers must never use UUID comparison instead of the explicit version or sequence fields.

## Tests and imports

- Domain tests use a deterministic injected generator and do not assert wall-clock UUID contents.
- Integration tests verify typed-ID round trips through PostgreSQL and transport serialization.
- Imported external identifiers are stored separately as `(source_system, source_id)` mappings. They never replace canonical UUIDs.
- Existing source IDs may be retained for traceability without creating a second canonical identity scheme.

## Security boundary

UUIDv7 values are identifiers, not secrets, access tokens, or authorization proofs. Authentication, session secrets, reset tokens, and signing material use dedicated cryptographic mechanisms. Exposing a UUID must not grant access to a resource; authorization remains mandatory.

## Acceptance criteria

ARC-003 is complete when every new persisted entity and event has one UUIDv7-backed typed ID strategy, tests can inject deterministic IDs, PostgreSQL uses native UUID columns, and event/business ordering does not depend on UUID sort order.
